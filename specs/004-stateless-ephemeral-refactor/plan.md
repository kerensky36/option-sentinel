# Implementation Plan: Stateless Ephemeral Refactor

**Branch**: `004-stateless-ephemeral-refactor` | **Date**: 2026-05-03 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/004-stateless-ephemeral-refactor/spec.md`

---

## Summary

Remove all database infrastructure from Option Sentinel and replace it with a fully stateless, ephemeral architecture. Live position and screener data is fetched from the Schwab API on demand per user request. User-authored metadata (thesis groups, spread definitions, exit goals) migrates to browser localStorage. Schwab OAuth tokens are stored in a signed session cookie. All alert infrastructure, the background scheduler, and SSE are deleted. The result is a FastAPI application deployable to GCP Cloud Run with scale-to-zero and no persistent storage of any kind.

---

## Technical Context

**Language/Version**: Python 3.11+
**Primary Dependencies**: FastAPI, Starlette SessionMiddleware, schwab-py, Pydantic, Jinja2, HTMX (frontend)
**Storage**: None (server-side); browser localStorage (client-side thesis/spread/exit-goal data)
**Testing**: pytest, pytest-asyncio
**Target Platform**: GCP Cloud Run (Linux container, single instance, scale-to-zero)
**Project Type**: Web service (personal trading dashboard)
**Performance Goals**: Cold start < 3 s; positions refresh < 5 s; screener refresh < 10 s
**Constraints**: max-instances=1, no mounted volumes, no Cloud SQL, < 256 MB RAM idle
**Scale/Scope**: Single trader, single Schwab account pair, < 50 open positions
